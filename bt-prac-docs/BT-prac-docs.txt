pragma solidity ^0.8.0;

contract SimpleBank {
    mapping(address => uint256) private balances;

    // 1. Deposit Money: Accepts incoming ETH and adds it to the caller's balance ledger
    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    // 2. Withdraw Money: Checks if you have enough funds, subtracts it, and sends ETH back to your wallet
    function withdraw(uint256 amount) public {
        require(balances[msg.sender] >= amount, "Not enough funds!");
        balances[msg.sender] -= amount;
        (bool success, ) = payable(msg.sender).call{value: amount}("");
        require(success, "Transfer failed!");
    }

    // 3. Show Balance: Reads and returns the caller's current balance (completely free, zero gas fee)
    function getBalance() public view returns (uint256) {
        return balances[msg.sender];
    }
}

We deposited Test Ether (ETH) into the smart contract to test that our deposit function actually worked on the blockchain and to make sure the contract could successfully receive and track real value.

Here is why that step is crucial:

Testing the Ledger: Depositing test ETH triggered the deposit() function, forcing the smart contract's balances mapping to record that your specific wallet address owns those funds.

Proving Value Transfer: Unlike a standard database, a smart contract handles real assets (even if they are test tokens). 
Depositing proves that the contract can accept incoming money, hold it safely in its code-controlled address, and accurately update balances before you attempt to withdraw or check your balance.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract StudentData {
    
    // 1. Structure to define a Student's blueprint
    struct Student {
        uint id;
        string name;
        uint age;
    }

    // 2. Dynamic Array to store a list of multiple students
    Student[] public students;

    // Function to add a new student to the array
    function addStudent(uint _id, string memory _name, uint _age) public {
        students.push(Student(_id, _name, _age));
    }

    // Function to retrieve total number of students
    function getStudentCount() public view returns (uint) {
        return students.length;
    }

    // 3. Fallback and Receive functions 
    // These execute if someone accidentally sends Ether directly to the contract or calls a function that doesn't exist.
    receive() external payable {}
    
    fallback() external payable {}
}

Step 2: Explanation of Key Constructs Used
Structures (struct): Allows you to create a custom data type (Student) that groups related variables together (id, name, age).

Arrays (Student[]): A dynamic list (students) used to store multiple instances of the Student struct on the blockchain.

Fallback & Receive Functions (receive & fallback): Special catch-all functions that handle incoming Ether transfers or missing function calls safely so the contract doesn't crash or reject funds unexpectedly.

Transaction Fee=Gas Used×Gas Price

1. Public Blockchains (Permissionless)
What it is: A completely open network where anyone in the world can join, read, write, and validate data. There is no central authority, and security is maintained through economic incentives and cryptography (proof-of-work or proof-of-stake).

Key Characteristics: Fully decentralized, transparent, and immutable, but typically slower and lower in transaction throughput.

Real-Time Use Cases:
Cryptocurrencies: Native digital assets like Bitcoin and Ether used for decentralized peer-to-peer value transfer.
Decentralized Finance (DeFi): Lending, borrowing, and trading assets without intermediaries using smart contracts (e.g., Uniswap, Aave).
NFTs and Digital Ownership: Tracking verifiable ownership of digital art, gaming assets, or event tickets.

2. Private Blockchains (Permissioned)
What it is: A restricted network controlled by a single organization or entity. Access, read, and write permissions are strictly managed and vetted.

Key Characteristics: High speed, high privacy, and centralized control or governance. It acts more like a distributed database with cryptographic guarantees.

Real-Time Use Cases:
Internal Supply Chain Management: Companies tracking inventory, manufacturing status, and asset movement across internal warehouses and subsidiaries.
Internal Auditing & Compliance: Enterprise record-keeping where tamper-proof logs are required for regulatory audits.
Central Bank Digital Currencies (CBDCs): Piloted by national central banks to control issuance and trace transactions securely among authorized commercial banks.

3. Consortium Blockchains (Federated)
What it is: A semi-decentralized network where consensus is controlled by a pre-selected group of organizations or stakeholders rather than a single entity.

Key Characteristics: Shared control, balanced privacy, and faster processing speeds than public chains.

Real-Time Use Cases:
Interbank Settlement Networks: Global financial messaging and settlement platforms used by multiple banks to clear international transactions faster.
Multi-Enterprise Supply Chains: Industry networks where competing companies (e.g., shipping lines, ports, and customs) collaborate on shared logistics data without exposing proprietary trade secrets.
Food Safety Tracking: Cross-industry tracking systems (like IBM Food Trust) where farmers, distributors, and grocery chains jointly verify product origins.

4. Hybrid Blockchains
What it is: A combination of public and private blockchains. It allows an organization to run a private, permission-controlled system alongside a public network, allowing certain data to be public while keeping sensitive data private.

Key Characteristics: Highly flexible, customizable privacy rules, and interoperable between closed and open systems.

Real-Time Use Cases:
Real Estate Tokenization: Publicly trading fractional shares of real estate tokens while storing private legal documents and user identity verifications behind a permissioned layer.
Healthcare Records Management: Patients share specific encrypted medical records publicly or across providers for verification, while personal identifying health histories remain strictly private.
